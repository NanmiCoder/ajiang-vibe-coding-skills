# 创建 PR 前：同步最新上游并检查业务冲突

**获取最新目标、集成、检查和验证是创建 PR 的必做步骤。** 所在目录是普通 checkout 还是 worktree，不改变这一要求。

## 1. 获取真正的 PR 目标

确认目标仓库、远程和分支。fork 的 `origin` 可能只是自己的仓库；PR 指向哪个仓库，就获取哪个仓库的目标分支。不要把本地 `main`、当前分支的 tracking upstream 或缓存的远程引用当成最新 PR 目标。

执行 `git fetch <目标远程>`，确认目标分支已被取回，记录目标 commit SHA。受限 refspec 未取回目标时显式获取该分支。fetch 失败或目标身份不明确时，不能宣称已同步。

## 2. 看上游新增变化并集成

记录同步前的来源 HEAD 和与目标的共同祖先。检查目标侧新增提交，以及双方从共同祖先以来的差异，找出交叉影响。

将获取的目标 SHA 合并或 rebase 到 PR 分支，遵循仓库策略。已发布分支不擅自改写历史；无既定策略时优先正常 merge。目标已是来源分支的祖先时不制造空合并，但仍核查范围和验证依据。

工作区有无关未提交改动，或分支被另一个 worktree 占用时，先保护已有工作，在干净的来源 worktree 或隔离位置集成。不要直接 `git pull` 当前 tracking 分支冒充目标同步，也不要为了更新目标而覆盖另一个 worktree。

在隔离位置完成集成的，最终结果必须安全落实到实际要推送的 PR 分支；不能测试一份合并结果，却推送同步前的另一份 HEAD。

## 3. 检查文本与业务冲突

文本冲突按两边原任务、业务意图和验收条件解决，不机械选择 ours/theirs。

**Git 合并成功不代表业务兼容。** 即使没有冲突标记，也要沿双方变化的调用链检查：

- 上游接口、参数、配置格式、单位或状态语义变化，是否仍被本次代码正确使用。
- 上游的删除、重命名、注册和迁移，是否让新功能落到旧入口或漏掉必要步骤。
- 双方改动的默认行为、错误处理与数据流，是否在组合后破坏原需求。

检查与本次交叉影响有关的路径，不把一次 PR 扩大成全仓审查。发现实质取舍无法从证据判断时，列出具体冲突与选项；不靠“能编译”决定业务正确。

## 4. 验证集成后的代码

在同步后的来源 HEAD 上，重跑原任务验收与双方交叉影响的相关回归，检查实际输出、状态或产物。关键业务结果不能只靠编译、lint 或 Git 无冲突证明。

已有失败与本次组合引入的失败分开记录。修复后在最终要推送的 HEAD 上验证；必要外部条件缺失时明确未验证项，不把同步前的通过当成集成后通过。

## 5. 发布前再核对一次

再次 fetch 并比较目标 SHA。若目标已变化，获取新增差异，重复集成与受影响路径的检查、验证，再发布 PR 分支。目标频繁前进且无法完成稳定验证时报告具体状态，不无限重试或跳过检查。

结果绑定最终核对的目标 SHA 与来源 SHA。PR 创建后目标仍可能变化；后续更新或合并时，按新目标重新检查相关变化，不宣称一次验证永久有效。
