# 代码审查

找出会影响用户结果的真实问题，并核实证据。仅要求 review 时交付发现，不直接修改代码。

## 梳理需求与改动

触发 review 后，主 Agent 先整理清楚本次改动要解决什么问题、预期行为是什么，以及要审查的范围，作为交给审查者的共同背景：

- 用户原始需求、后续确认的调整、验收条件与项目规则。
- 目标仓库与工作区、本次改动范围及对应版本，明确是工作区改动、某个提交、分支差异还是 PR，并提供可读取的 diff。
- 必要的原始材料，如问题复现条件、相关输入与检查结果。

背景应足以让未参与实现的审查者自行判断，不夹带主 Agent 的实现推理、原因猜测或正确性结论。

## 交给独立 Agent 审查

主 Agent 将上述背景交给独立的审查 Agent。默认使用一个；用户要求多个时并行审查，指定数量时按指定数量执行，未指定数量时按改动范围安排。多个审查者使用相同的需求与目标版本，可分别关注需求实现、调用链与回归风险，独立形成发现后再汇总。

审查 Agent 使用独立上下文，不继承主 Agent 的完整对话和实现过程，自行读取代码并判断。使用当前环境提供的委派能力，不限定客户端、模型、工具名称或调用参数。

审查 Agent 负责只读审查与必要验证，不继续委派；验证所需写入放隔离位置。主 Agent 负责交接、核实发现与汇总。当前环境无法提供独立上下文、委派或所需并行能力时，说明具体限制和实际采用的方式，完成可执行的审查，不将主 Agent 自审或串行审查称为独立并行审查。

## 检查实际行为

审查 Agent 先读 diff，再跟进相关调用者、数据来源和实际使用代码，区分本次改动与无关旧问题。不能仅凭改动文件里的片段判断整条流程正确。

从用户入口检查：需求是否实现，正常输入是否得到预期结果，错误、边界、取消、恢复与资源清理是否正确。涉及平台、协议、存储或配置时，再检查对应差异。

优先关注能导致错误结果、数据丢失、行为回归或任务无法完成的问题。风格偏好、可以优化的写法与实际 bug 分开，不为了凑数量报告问题。

## 核实每条发现

每条问题写清：

- 文件与具体位置。
- 什么条件下触发，用户会遇到什么后果。
- 对应调用或数据路径。
- 复现实验或完整代码路径证据。
- 是本次引入的问题，还是已有问题。

主 Agent 核实审查者提交的发现，对关键发现运行有区分力的验证；不便复现时给出可核查的代码路径，并明确缺少什么证据。区分已确认、可疑与待确认，合并重复发现；多个审查者同意也不能代替证据。

只在已授权修复时修改已确认且与任务相关的问题，再重跑对应失败场景和受影响路径。后续提交或合并改变代码后，复核相关变化，不能沿用旧版本的结论。

## 输出结果

先列有证据的问题，按影响排序，再简述验证与未覆盖范围，以及实际审查方式、审查者数量和独立上下文情况。没有已确认问题时说明检查过的范围，不声称保证无 bug。

多轮审查可用 [代码审查记录](assets/task-record.md) 保存发现、证据与复核结果。
