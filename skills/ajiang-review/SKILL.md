# 代码审查

找出会影响用户结果的真实问题，并核实证据。仅要求 review 时交付发现，不直接修改代码。

## 确定审查范围

读取项目规则、原需求与验收条件，确认要审查的是工作区改动、某个提交、分支差异还是 PR。记录对应版本，区分本次改动与无关旧问题。

先读 diff，再跟进相关调用者、数据来源和实际使用代码。不能仅凭改动文件里的片段判断整条流程正确。

## 检查实际行为

从用户入口检查：需求是否实现，正常输入是否得到预期结果，错误、边界、取消、恢复与资源清理是否正确。涉及平台、协议、存储或配置时，再检查对应差异。

优先关注能导致错误结果、数据丢失、行为回归或任务无法完成的问题。风格偏好、可以优化的写法与实际 bug 分开，不为了凑数量报告问题。

用户要求独立审查，或高影响改动确有需要且当前允许委派时，可以使用独立 agent。给它原任务、目标 diff、验收条件和必要原始材料，不传“这一定正确”的结论。审查者只读源码，验证所需写入放隔离位置。没有独立 agent 时直接审查，并如实说明方式。

## 核实每条发现

每条问题写清：

- 文件与具体位置。
- 什么条件下触发，用户会遇到什么后果。
- 对应调用或数据路径。
- 复现实验或完整代码路径证据。
- 是本次引入的问题，还是已有问题。

对关键发现运行有区分力的验证；不便复现时给出可核查的代码路径，并明确缺少什么证据。区分已确认、可疑与待确认，合并重复发现；多个审查者同意也不能代替证据。

只在已授权修复时修改已确认且与任务相关的问题，再重跑对应失败场景和受影响路径。后续提交或合并改变代码后，复核相关变化，不能沿用旧版本的结论。

## 输出结果

先列有证据的问题，按影响排序，再简述验证与未覆盖范围。没有已确认问题时说明检查过的范围，不声称保证无 bug。

多轮审查可用 [代码审查记录](assets/task-record.md) 保存发现、证据与复核结果。
