# 从用户任务到最小实现

## 使用边界与准备

此 skill 可单独安装，必要方法都在本文件中，不依赖作者本机或其他 skill。先读取目标项目规范，确认目标仓库/工作区、版本、用户结果和允许的改动；参考仓库只读。没有项目规则时读取实际 README、脚本和源码推导入口。

按当前可用且获授权的工具执行：缺少独立 agent 可使用新会话/人工审查或分视角自检，注明真实审查方式；缺少浏览器/真实 API 时完成可执行部分并交接未覆盖验收，不能冒充独立审查、GUI 或真实服务通过。项目本来的运行环境仍需具备；不绑定模型厂商或特定插件。

复杂任务可按 [assets/task-record.md](assets/task-record.md) 保存必要事实；简单任务直接记录结果，不机械增设流程。

## 定义可观察结果

把需求落成“什么人在什么条件下做什么动作，应观察到什么结果”。有现成失败、截图或参考实现时读取它；明确目标项目与参考材料的身份，防止把参考仓库改了。

从实际入口找现有链路和可复用模块；复用前检查其真实契约，不凭命名推断。需求不明确时先推进不依赖该信息的调查，再询问影响结果的关键差异。无须为每次小改写一份规格。

## 最小纵向切片

优先打通一条完整用户路径：输入 → 状态/业务执行 → 实际输出，而非铺满所有抽象层再做演示。沿用现有栈和结构。记录必要行为与本次不涵盖的需求，不擅自扩展成平台重建。

对比可获得的参考实现时给出设计前提、值得复用的部分与应保留的现有能力；没有源码就只对可观察行为做判断。参考代码是证据，不意味着自动迁移其技术栈。

修改涉及配置、事件、provider、存储或进程边界时，从实际生产者跟到消费者，检查来源、优先级、缺失状态、错误传播和恢复行为，并用对应负向场景验证。触及支持语言、主题或平台时覆盖相应变化；项目不支持的能力不因本流程变成新需求。

## 对结果验证

从项目真实入口执行最小用户任务，检查实际输出或持久化状态。按改动加入关键失败或边界场景，运行现有相关检查。开始时已失败的检查记录为基线，不能把它们静默忽略或归因于本次代码。

真实外部服务变化需要真实边界证据；没有资源时交代未验证部分并完成内部检查。检查不会抓住错误实现时，改进断言而非堆数量。

本次新增问题必须处理，无关旧问题记录后续。复杂/高影响变化或用户要求独立 review 时，给独立审查者任务、验收、目标版本和原始事实，不给作者结论；每条发现必须有触发条件与实际后果，逐条核验后再修复。普通小修改可直接交付。

## 完成与连续迭代

用户已授权提交/集成时，只提交本次范围，核对最新目标和语义冲突，在集成状态复测；已授权发布时，核对版本和 notes，观察 CI 并验证实际产物。仅要求实现时，提交准备与外部发布不能替代实际实现。

下一轮或另一会话接手时保留：用户结果、当前版本、有效配置、已验证内容、已排除假设的适用条件、剩余问题及允许的下一步。记录是项目的动态事实，不升格为所有未来任务的永久规则。
